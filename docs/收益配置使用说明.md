# 收益配置使用说明

## 充值分红与会员自行提现（本次本地改动，尚未上线）

门店操作放在「日常业务 → 收益管理 → 充值分红与会员提现」：

1. 首次点击「启用充值分配」。系统会提示旧手填积分池的处理：保留为待核对记录，不把手填金额当成真实充值；已经入账的收益和购买权益保留。
2. 输入金额，点击「创建充值单」。记录自动展开，显示微信返回的充值银行账户；门店按该笔金额向该账户转账，不要重复转入。
3. 系统核实充值进入商户运营账户后，自动按核实当时有效认证会员的份数分配到小程序余额。银行到账有延迟，创建充值单或填写金额不代表已到账。
4. 会员在小程序「我的 → 我的收益」查看可提现余额，输入金额申请提现，在记录中点击「确认微信收款」。未开通微信通道时按钮禁用、余额保留。

沿用当前六档认证方案及 1/2/4/8/16/32 份规则，会员资格仍由后台核对已付款订单后认证。推荐奖励、兑换积分、预约、商品权益不因充值方式变化而改变。

每笔充值独立分配，不再等到晚上重复结算。首次核实到账时冻结名单和份额，之后改方案、退款、刷新或重启不会重分这笔充值。到账时没有合格会员则保留资金，后台核对后再分配。「今日充值分红」次日归零，但个人累计余额不归零。

提现中的金额被占用，不能同时提现或人工兑现；微信确认成功才记实际出款，明确失败或取消后释放占用。断网、响应丢失沿用原单核对，不能换单重复发钱。已排队或已发起的旧转账继续核对，旧收益不会因开启通道而新增自动转账。旧手填未分配金额保留待核对，不自动转成充值。

接入配置：

- `WECHAT_RECHARGE_ENABLED=true`：需商户先取得「商家充值」接口权限，并配置现有 `WECHAT_PAY_*` 商户签名与微信验签参数。充值固定进入同商户的运营账户。
- `WECHAT_TRANSFER_ENABLED=true`：需开通商家转账能力，配置已批准的真实场景、报备信息、通知地址及小程序绑定关系。新提现采用用户确认收款模式；原授权转账模式不改。
- `WECHAT_WITHDRAWAL_MAX_AMOUNT=200`：新提现的单笔上限，须按商户实际获批额度配置；默认 200 元，页面显示当前限额。该配置不改变旧每日转账。微信的实际单日和单用户限额仍以商户平台为准。
- 上述开关默认关闭。程序配置完整只表示可以发起请求，不等于微信已经批准商户权限；正式启用前仍需小额真实充值、分配及真机提现验收。
- 密钥只放服务端配置，不放页面或小程序。后台读取/操作分别使用现有 `anqi:earnings:list`、`anqi:earnings:edit` 权限；会员只能查询和提现本人的余额。
- MySQL 启动会按现有建表机制增加 `anqi_recharges`，保留现有数据。转账超过微信 30 天查单期限会停止自动续办并保留占用，需要核对原商户资金账单，不能重新发钱。

本地验证命令：

```sh
node --test tools/wallet.test.cjs tools/shareholder-transfers.test.cjs
node tools/wallet-acceptance.cjs
npm run build:h5
node tools/wallet-ui-acceptance.cjs
```

上述测试使用临时数据和本地微信接口替身，不连接线上；不代表真实微信资金验收已经完成。

接口依据：[申请银行转账充值](https://pay.wechatpay.cn/doc/v3/merchant/4012585425)、[查询充值结果](https://pay.wechatpay.cn/doc/v3/merchant/4012585430)、[商家转账查单](https://pay.wechatpay.cn/doc/v3/merchant/4012716437)。

## 股东按份数每日分配（未切换充值模式时适用）

本次改动尚未更新线上。新规则默认关闭，由后台明确启用；切换后，以本节为准。下面保留的套餐及 5% 分红说明适用于尚未切换的旧规则。

门店日常操作：

1. 在「收益管理 → 股东每日分配 → 方案与结算设置」查看六档固定方案与份数，设置每日结算时间；可停止某档新认证，已结算金额不重算。
2. 在「会员管理 → 股东认证」核对该顾客已付款的订单，选择分配方案并确认。单纯购买商品、登记会员或者开通收益开关，不会自动认证股东。
3. 每天在「股东每日分配」填写一次当天公共积分池总额并保存。到设置的北京时间自动结算，无需逐个给会员加积分。只分给有效认证股东，包含之前加入且仍有效的股东。

小程序公共积分池显示当天总额，次日显示零，直到录入当天新总额；「我的积分」显示本人的当日预计或已结算分配。原签到、兑换积分独立保留为「兑换积分」。收益累计和兑现记录保留。

认证股东才获得专属码及邀请权限。专属码、微信转发链接、后台推荐人选择使用同一资格判断。首单 50%、后续 10% 继续使用现有「推荐奖励」配置；原来关闭时需按原入口启用。新单在付款时记录股东资格，选择“订单完成后入账”也沿用付款时的资格。历史邀请及旧订单不自动补奖励。

保护规则：旧静态收益计划或带旧静态收益承诺的订单未处理完时，禁止直接切换；同一天不能同时按旧池和新池分配。金额计到分、结算防重，更新有版本校验。已经使用的旧体验卡继续使用原权益。

### 微信到账与分配记账

录入积分池是记账操作，不是给微信商户充值。微信转账默认关闭；启用真实转账前，需要商户实际开通对应能力、备妥商户资金与密钥，并完成真机到账验收。

- `WECHAT_TRANSFER_ENABLED=true`：启用自动转账工作进程；仍需所有商户参数完整。
- `WECHAT_TRANSFER_MODE=confirm`：默认每笔由用户在小程序确认收款；`authorized` 为商户具备授权转账能力时使用，首次由用户授权，后续查询有效授权再转账。
- `WECHAT_TRANSFER_SCENE_ID`、`WECHAT_TRANSFER_SCENE_REPORTS`：填写微信商户平台批准的真实转账场景及报备信息，不预填虚构内容。
- `WECHAT_TRANSFER_NOTIFY_URL`：公网 HTTPS `/api/transfer-notify` 地址。
- 复用既有 `WECHAT_APPID` 和 `WECHAT_PAY_*` 商户签名、APIv3 密钥、微信支付公钥配置，不在后台页面存储密钥。

系统仅以验签成功、金额及收款账号一致的微信查单结果记“已到账”；用户点击确认不代表到账。处理中金额预留，不能再人工兑现；结果不明保留原商户单号查询，确定失败后才允许核对重试。开启通道不会自动补转以前已结算的历史收益。

目前验证范围：16 项新增自动化检查，隔离 API 流程及重启持久化，320/375/430 宽度的小程序相关页面与后台认证/配置操作，以及支付、退款、套餐、补录、邀请和旧分红规则回归。小程序、后台与 Java 编译通过。真实微信转账和手机端原生收款确认尚未验收。

相关本地验收命令：`node --test tools/shareholder-program.test.cjs tools/shareholder-transfers.test.cjs tools/shareholder-share.test.mjs`、`node tools/shareholder-flow-acceptance.cjs`。页面验收先执行 `npm run build:h5`，再执行 `node tools/shareholder-ui-acceptance.cjs`（使用本机 Playwright/Edge，接口全部模拟）。

## 旧规则说明（未切换股东分配时适用）

## 在后台设置

进入「日常业务 → 收益管理 → 收益规则」，点击对应VIP套餐的「配置」。六档套餐分别设置，默认均未启用，系统不代填实际奖励金额。

- **静态收益**：给购买该套餐的会员。选择固定金额或订单实付比例，设置每期金额/比例、首次等待天数、间隔天数和总期数。
- **动态收益**：给邀请人。第1级为直接邀请人，第2级为邀请人的邀请人，最多10级。各级可独立开关、配置金额/比例、起算条件与等待天数；每个层级每笔订单只入账一次。
- **起算条件**：确认收款后，或整套套餐所有项目核销完成后。选择“整套完成”时，核销其中一次不触发收益。
- **整单退款**：可选“取消未入账并冲回已入账”或“取消未入账、保留已入账”。退款仍沿用现有订单限制：已使用套餐不支持整单自动退款，部分退款未实现。
- **保存前试算**：输入示例实付金额，查看静态每期及累计金额、全部层级都有合格邀请人时的动态总额。试算不写账。

## 推荐奖励（直接推荐人）

在「收益规则」页顶部的「推荐奖励 · 直接推荐人」点击「配置」。默认值为首单 50%、之后每单 10%、所有已付款订单、不限期，**默认关闭**，启用后才对新订单生效。

- **奖励对象**：只奖励被推荐人首次绑定的直接推荐人，推荐人的推荐人不奖励；推荐人已停用、自己推荐自己时不奖励。已有账号在下单前扫码也可自动绑定，已有推荐关系不会被覆盖。
- **首单与后续**：首单指被推荐人第一笔已付款且未退款的适用订单，按付款时间判断；启用前已付款的历史订单同样计入，因此老顾客的下一单按后续订单计算。首单整单退款后，下一笔付款订单按首单计算。
- **适用订单**：所有已付款订单（含普通商品、服务和VIP套餐），或仅VIP套餐订单。体验卡、贵宾卡领取和积分兑换不是订单，不产生推荐奖励。
- **其他设置**：起算条件（确认收款后或订单完成后）、入账等待天数、推荐有效天数（从被推荐人注册起算，0为不限）、整单退款时冲回或保留。
- **与套餐动态收益的关系**：推荐奖励启用后，各套餐中配置的多级动态收益不再对新订单发放，避免同一订单重复奖励；静态收益不受影响。
- **账本显示**：发放计划和入账明细标为「推荐 · 首单 / 后续」；小程序「我的收益」显示「推荐奖励（首单 50%）」等说明，计入动态收益合计。

示例：被推荐人首单买 1,980 元焕颜套，推荐人得 990 元；第二单买 6,980 元黄金VIP套餐，推荐人得 698 元。

## 分红池（静态收益 · 超级VIP会员）

在「收益规则」页的「分红池」点击「配置」。默认规则为：**每天拿出当天营业额的 5%，3 天一轮，分给本轮已办卡的超级VIP会员**（办任意一档VIP套餐即为超级VIP会员），**默认关闭**。

- **奖池**：当天营业额（当天付款、期末前未退款的全部订单实付合计，含商品、服务和VIP套餐）× 比例。也可改为「当期新增办卡金额 × 比例」或「固定基数 × 比例」。当天营业额为 0 时不分配。
- **3 天一轮**：第 1 天分给当天办卡的会员；第 2 天分给第 1、2 天办卡的会员；第 3 天分给第 1–3 天办卡的会员；第 4 天开始新一轮，只分给新一轮办卡的会员。本轮开始前办卡的会员不参与本轮。轮次从开始日期起计算；活动天数可改，设为 0 则每天分给全部持卡会员。分轮活动只适用于按天结算。
- **分配**：按会员在本轮内的办卡金额占本轮参与会员办卡金额合计的比例分配，计到分，零头按比例余数从大到小补齐，每天发放总额等于奖池。已停用会员不参与。
- **结算时间**：北京时间每天 0 点后自动结算前一天，停机后补算；同一天只结算一次。
- **退款**：按当天结束时的状态判断：当天结束前退款的不计入营业额、也不参与分配；当天结束后才退款的（含零点后、尚未结算时）仍计入当天，从下一天起不再参与。已发分红不冲回。
- **开始日期**：留空或早于今天时从今天开始（即第 1 轮第 1 天）；不补发启用前或关闭期间的日子；中途修改时从已结算的最后一天之后开始，不会重复分配。
- **与套餐静态收益的关系**：分红池启用后，各套餐中配置的静态收益不再对新订单发放。
- **记录**：后台卡片实时显示本轮第几天、本期到目前的营业额和预计奖池；「分红记录」页按天列出轮次、奖池、实发、参与会员和办卡总额；会员明细在「入账明细」中显示为「分红池 日期（第N轮活动第N天）」，小程序「我的收益」计入静态收益。

示例：第 1 天 A 办 6,980 元的卡，当天营业额 8,960 元，奖池 448 元全部给 A；第 2 天 B 办 13,800 元，营业额 13,800 元，奖池 690 元由 A、B 按 6,980 : 13,800 分；第 3 天 C 办 26,800 元，奖池 1,340 元由 A、B、C 分；第 4 天 D 办卡，开始第 2 轮，奖池只给 D。

## 规则何时生效

规则及邀请关系在订单创建时保存快照。修改、关闭规则只影响之后创建的订单，已有订单和发放计划继续按原版本执行。上线前订单、未配置收益时创建的订单不会自动补发。并发修改同一套餐会提示版本冲突，需刷新后重新编辑。

动态收益沿首次绑定的邀请关系逐级查找，不根据签到、购买次数或静态收益再产生收益。下单时缺失、停用的邀请人不奖励、不向其他级补位；循环关系和自己邀请自己不会重复奖励。下单后停用收益接收会员会暂停计划入账，恢复后补记到期金额。绑定前已创建的订单不会补算奖励。

## 账本与计划

- 后台「发放计划」查看来源订单、规则版本、金额、期数与下一次到期时间；「入账明细」查看实际正向入账及负向退款冲回。
- 小程序「我的 → 我的收益」显示静态、动态收益、累计净收益和待入账计划，可按类型筛选。启用的静态收益规则也显示在套餐下单确认页。
- 时间按北京时间展示。等待天数、间隔天数均为完整的24小时，非自然月；例如间隔30天不等同于每个自然月同一天。
- 后台每分钟检查到期计划，读取收益页时也补记；服务停机后会补记已到期部分，每轮最多2000笔，大量积压会分轮处理。
- 金额使用整数分，比例最多两位小数，单期结果四舍五入到分。重复收款事件、并发访问、重启不会重复入账。
- 退款冲回追加负数记录，保留原始收益记录。退款不删除账本，未入账计划会取消。
- 历史旧收益记录保留为“历史收益”，计入累计净收益，不擅自归入静态或动态类别。

## 权限与接口

- 后台查看使用 `anqi:earnings:list`，修改规则使用 `anqi:earnings:edit`。角色的会员查看权限决定是否能显示会员姓名；未授权时仅显示编号。
- 后台接口：`GET /anqi/incomeRules`（含 `referral` 推荐奖励、`pool` 分红池设置及 `poolOverview` 分红记录）、`PUT /anqi/incomeRules/{productId}`、`PUT /anqi/incomeRules/referral`、`PUT /anqi/incomeRules/pool`、`GET /anqi/incomePlans`、`GET /anqi/earnings`。推荐奖励沿用 `anqi:earnings:edit` 权限，Java 代理无需修改；设置保存在业务配置 `referralReward`、`poolReward` 中；分红结算记录新增数据集合 `poolSettlements`，MySQL 模式下服务启动时自动建表 `anqi_poolSettlements`，无需手工执行 SQL。
- 顾客接口：`GET /api/earnings-summary` 返回本人汇总及计划；原 `GET /api/earnings` 保持数组结构。
- 新表：`anqi_incomeRules`、`anqi_incomePlans`；原 `anqi_earnings` 追加收益记录。规则快照存于订单内部，不返回邀请链或管理员信息给顾客。
- 更新Java代理、Node业务服务与管理前端，执行后端仓库的 `sql/anqi-income-config.sql` 更新菜单，不自动授权其他角色。
